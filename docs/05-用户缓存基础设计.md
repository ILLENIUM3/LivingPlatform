# 用户缓存基础设计（阶段 02 扩展）

日期：2026-11-09。本次实现 Cache Aside、空值缓存、TTL 抖动和事务提交后失效。尚未实现缓存重建锁、失效事件持久化、消息重试或延迟双删。

## 1. 与参考项目的对应关系

参考 qiyu-live `UserServiceImpl.getUserById` 的“读 Redis → 查库 → 回填”，以及 `updateUserInfo` 的更新后删除缓存。原项目后续使用 Kafka 延迟删除；我们的首版先明确数据库事务边界，再逐步实现可靠失效。

API 和 RPC 契约不变，缓存仅位于用户 Provider 内部。数据库仍是事实来源，不能通过缓存值决定是否允许修改用户。

## 2. 阅读顺序

1. `UserCacheProperties`：缓存开关、Key 前缀、TTL 与抖动范围。
2. `UserCache`：Redis 读取、JSON 编解码、空值标记和过期时间。
3. `UserService.getById`：串联缓存与数据库。
4. `UserChangedEvent`：用户创建、修改后发布的进程内事件。
5. `UserCache.onUserChanged`：数据库提交成功后删除缓存。

类路径均位于 `backend/live-user-provider/src/main/java/com/liveplatform/user/provider`。

## 3. 查询与空值缓存

```text
校验 userId
  → 事务内调用：直接查库，不读取或回填缓存
  → 普通调用：读取 Redis
      → 命中用户：返回用户资料
      → 命中空值：返回 USER_NOT_FOUND
      → 未命中 / Redis 故障 / JSON 无效：查询数据库
          → 存在：写入普通缓存，返回资料
          → 不存在：写入短期空值缓存，返回 USER_NOT_FOUND
```

默认 Key 为 `live-platform:dev:user:v1:{userId}`。使用 StringRedisTemplate 保存显式 JSON，结构为 `schemaVersion`、`missing`、`user`。不存在的用户保存 `missing=true, user=null`，与 Redis Key 不存在区分。

普通缓存 TTL 为 1800～2100 秒，空值缓存为 30～40 秒，均在写入时加随机抖动。命中读取不续期，避免热点数据因不断访问长期不过期。短期空值缓存减少相同无效 ID 对数据库的重复查询，但不能阻止攻击者不断尝试不同 ID；入口限流留到后续阶段。

缓存内容不符合结构或用户 ID 不匹配时按未命中处理，重新查库，不把损坏的缓存作为业务结果。

## 4. 为什么在事务提交后删除

`create` 和 `updateProfile` 在事务内直接读取数据库结果，并发布 `UserChangedEvent`。监听器声明 `@TransactionalEventListener(AFTER_COMMIT)`，只有事务成功提交才删除对应 Key；事务回滚时不会执行删除。

创建也要失效缓存：某个尚不存在的自增 ID 可能曾被查询并产生空值缓存。创建成功后删除该 Key，可避免继续返回“用户不存在”。

事务内查询不回填缓存，防止事务最终回滚后 Redis 留下未提交的数据。修改资料的版本检查继续由 SQL 乐观锁完成，不依赖缓存里的版本判断成功与否。

## 5. 一致性与故障边界

本阶段提供的是带过期时间的最终一致性缓存，不保证更新完成后的每次查询都立即读到新值。

存在如下并发窗口：

```text
请求 A：缓存未命中，从数据库读到旧值
请求 B：更新数据库 → 提交 → 删除缓存
请求 A：把先前读到的旧值写回缓存
```

此外，数据库提交与删缓存之间可能进程退出，Redis 也可能拒绝删除。本轮事件只存在进程内，没有可靠投递保证。当前通过日志暴露失效失败，依靠最后一次旧值写入后的 TTL 收敛；下阶段再设计持久化失效事件、重试和并发回填处理。

Redis 读写故障不会改变数据库查询结果；提交后删除失败也不会伪装成数据库回滚。Redis 连接与命令超时均为 500ms，故障请求仍可能产生额外等待。大量请求回退会增加数据库压力，本轮没有实现熔断、限流或热点互斥重建。

Spring Boot 默认 Redis 健康检查保留：Redis 不可用时整体健康接口可能显示 DOWN，但用户业务可回退到数据库。健康状态与单个业务请求是否能成功需要分别理解。

## 6. 部署与配置

新增 `spring-boot-starter-data-redis`，版本由现有 Spring Boot 3.5.16 管理。没有升级 Java、Dubbo 或 Spring Boot。

Compose 新增本地 Redis `redis:7.4.2-alpine`，端口 `127.0.0.1:16379`，内存上限 128MB，使用 allkeys-lru 淘汰，关闭持久化。它目前只保存可重建的缓存，不得直接拿来存放不能丢失的钱包数据、可靠消息或后续锁等状态。

从项目根目录执行：

```powershell
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d redis
mvn -f backend/pom.xml -DskipTests package
```

已有阶段 01/02 数据库继续使用，无新增 SQL；如果尚未执行用户表脚本，先按阶段 02 文档执行 002 SQL。重新启动用户 Provider，使新依赖和配置生效。沿用 local API 调试接口即可操作用户。

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| REDIS_HOST | 127.0.0.1 | Redis 地址 |
| REDIS_PORT | 16379 | 本地映射端口 |
| REDIS_PASSWORD | 空 | 本地无密码；外部实例按实际配置 |
| REDIS_DATABASE | 0 | 数据库编号 |
| USER_CACHE_ENABLED | true | 关闭时跳过缓存读写和失效 |
| USER_CACHE_KEY_PREFIX | live-platform:dev:user:v1: | 不同环境/数据库使用不同前缀 |

TTL 在应用 YAML 的 `live.user-cache` 下配置，四个值均以秒为单位。所有用户服务实例必须使用一致的 Key 前缀和开关。若停用期间数据库发生修改，重新启用时应切换新前缀或清理旧的用户缓存，避免重新使用旧数据。

## 7. 手动观察方法

无需执行压测即可学习本轮行为：

1. 使用 `scripts/users.http` 创建用户，并查询两次。
2. 查看其 Redis 数据和剩余 TTL；第二次查询应命中缓存。
3. 修改资料后查看该 Key，提交后应被删除；再次查询回填新版本。
4. 查询一个不存在的正整数 ID，查看其短期空值缓存。

```powershell
# 将 1 替换成实际用户 ID
docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T redis redis-cli GET live-platform:dev:user:v1:1
docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T redis redis-cli TTL live-platform:dev:user:v1:1
```

需要查看命中情况时，启动 Provider 加参数 `--logging.level.com.liveplatform.user.provider.cache=DEBUG`。日志只输出用户 ID 和命中状态，不输出完整用户资料。
