## 2. 用户缓存与一致性

参考第一篇教程的 Redis 缓存和延迟删除思路，分两步实现。

### 基础版本

- MySQL 为事实来源，用户读取采用 Cache Aside：先读缓存，未命中再查库并回填。
- 更新数据库事务成功后删除缓存；事务失败不修改缓存。
- 查询不存在的用户时缓存短 TTL 的空值，普通数据 TTL 加随机抖动。
- 将 Redis Key 规范、TTL 和序列化方式集中管理，缓存对象与数据库对象分离。

### 一致性增强

数据库提交后删缓存仍然存在两个窗口：删除失败，以及并发读将旧值重新回填。为用户更新建立持久化失效事件（Outbox，与用户更新在同一数据库事务中写入），由任务或消息消费者重试失效操作；增加延迟失效降低旧值回填窗口，并用 TTL 限定残留时间。

该方案提供最终一致性，不能宣称延迟双删实现强一致。若业务要求更严格，再引入数据版本号和有版本的写入规则。事件重复执行必须安全，并记录重试次数与积压情况。

缓存击穿处理在基础缓存之后加入：对热点 Key 的缓存重建使用短期互斥锁，获取锁后再次检查缓存。获取失败时有限等待或降级，不无限递归重试。

## 3. 分布式锁与并发边界

参考 Redis Starter 和钱包、库存中的并发处理，把“资源互斥”和“最终数据正确”分别设计。

- Redis 加锁使用原子 SET NX PX，锁值采用每次持锁独有的随机令牌。
- 解锁用 Lua 比较令牌后删除，防止旧请求删除新持有者的锁。
- 等待有次数和总时长上限；锁只包围必要的短操作。
- 锁超时后旧请求仍可能继续执行，因此数据库唯一约束、带条件更新或版本号负责最终防重和冲突判定。
- 对可能超过租期的操作，设计可靠续期或采用适当的锁库；不把“设置了过期时间”当成任务完成的保证。

钱包扣款以数据库条件更新和本地事务为准：余额足够才扣减，同时写入唯一业务流水。请求号具有唯一约束，重复请求查询原结果；金额使用整数最小单位。Redis 余额仅在后续优化阶段引入，不能让一次异步写库失败造成账务丢失。

## 4. IM 与消息路由

参考第二篇教程，保留 `im-core-server`、`im-provider`、`im-router` 的职责划分。

### 单节点阶段

Netty 接收 WebSocket 连接，按消息类型分派登录、心跳、业务消息和 ACK。完成 IM Token 校验后绑定用户和连接，发送者身份由服务端会话确定。房间广播校验成员关系，断线清理连接与房间成员状态。

消息协议包含协议版本、消息类型、messageId、roomId 和消息体；客户端时间不作为权限或顺序判断依据。限制消息长度、单连接发送频率和待发送队列长度，避免慢客户端造成无界内存增长。

### 多节点阶段

在 Redis 保存用户与 IM 节点的在线路由，路由带会话标识和过期时间。心跳续期；旧连接断开时按会话标识清理，避免误删重连后的新路由。

Router 按节点批量分组投递房间消息。ACK 表示约定范围内的接收确认；超时重投使用同一 messageId，接收端去重。重试有上限，关键事件可查处理状态，不能承诺网络层恰好一次送达。

聊天消息与钱包业务结果分别处理。重连补偿、离线消息保留范围、单用户多端策略在单节点版本完成后明确。

## 5. 送礼与异步可靠性

参考第三篇教程，先完成同步送礼链路，再用 Kafka 异步化。

送礼请求先保存稳定请求号和处理状态。钱包以同一请求号幂等扣款，成功后完成礼物记录与广播。跨服务超时不等于扣款失败，需要查询原交易结果后决定继续或补偿。

异步版本使用持久化事件、消费幂等和失败重试。API 明确区分“已受理”和“处理完成”。礼物动画允许事件去重，但扣款不能依赖动画 ACK 判定成功。

## 6. PK、红包与库存

| 场景 | 实现重点 | 数据正确性约束 |
| --- | --- | --- |
| PK | 会话 ID、活动状态、Lua 原子计分、事件序号 | 礼物事件重复不重复计分，旧会话消息不能修改新会话 |
| 红包 | 原子领取、用户去重、领取记录和钱包入账 | 已领取总额不超预算，重复投递不重复入账，剩余金额有结算规则 |
| 秒杀 | Lua 预扣库存、订单状态机、超时取消 | Redis 预扣与持久化失败需补偿，回补只能执行一次，数据库也应防止超卖 |

Lua 只保证单次 Redis 脚本的原子性，不覆盖 MySQL、Kafka 或其他服务。每条跨系统链路都需要稳定业务号、可恢复状态和补偿边界。

4. 登录鉴权和直播间业务。
5. 单节点 IM、视频接入。
6. 钱包与礼物的同步正确性。
