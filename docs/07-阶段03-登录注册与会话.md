# 阶段 03：登录注册与会话

日期：2026-11-10。承接阶段 02 的用户基础、Redis 缓存与热点重建锁。本阶段交付模拟短信登录、自动注册、会话查询、过期和退出；下一阶段为 Gateway 与登录页面。

## 1. 用户现在能做什么

本地申请验证码后，首次登录自动创建用户，后续用同一手机号登录会得到同一个用户 ID。登录返回随机 Token，客户端使用 `Authorization: Bearer <token>` 查询当前用户；退出后该 Token 失效。

这里的“会话”就是 Redis 中一条有期限的 `Token 摘要 → 用户 ID` 记录。用户 ID 来自服务端映射，传入 `userId` 参数或 `X-User-Id` 请求头不能代替登录。

默认策略：验证码 6 位、有效期 300 秒、同一手机号 60 秒内不能重发、每个验证码最多输错 5 次；Token 固定有效期 7 天，访问不续期。允许多个设备同时登录，退出只影响当前 Token。

模拟短信不实际发送：仅当 **Provider 激活 `local` profile 且 `AUTH_MOCK_ENABLED=true`** 时，获取接口才在 `data.mockCode` 回显随机验证码。默认关闭，未配置真实短信供应商时返回 503，不能把此回显接口当作公网登录服务使用。

## 2. 接口契约

统一响应继续使用 `code/message/data/requestId`。手机号和验证码按字符串传递，验证码保留前导零；本阶段手机号格式为 `1[3-9][0-9]{9}`，仅做格式校验，不代表验证了运营商号段。

| HTTP | 请求 | 成功结果 |
| --- | --- | --- |
| `POST /api/auth/code` | `{"phone":"13800138000"}` | `mockCode`、`expiresInSeconds`、`resendAfterSeconds` |
| `POST /api/auth/login` | `{"phone":"13800138000","code":"012345"}` | `token`、`tokenType=Bearer`、`expiresInSeconds`、`user` |
| `GET /api/users/me` | Authorization 请求头 | 当前用户资料；`id` 为字符串，不含手机号 |
| `POST /api/auth/logout` | Authorization 请求头 | `data=null`；重复退出或已过期仍返回成功 |

四个接口成功均返回 200，并设置 `Cache-Control: no-store`。缺失或格式错误的 Bearer 返回 401；退出时格式正确但已不存在的 Token 视为成功。资料修改的 `PATCH /api/users/me` 留到阶段 04 结合统一鉴权实现，当前 `/api/dev/users` 仍只用于 API 的 `local` 调试模式。

| 错误码 | HTTP | 含义 |
| --- | --- | --- |
| `INVALID_ARGUMENT` | 400 | 手机号、验证码或请求格式错误 |
| `AUTH_CODE_INVALID` | 400 | 验证码错误、过期、已消费或超过错误次数；不透露具体状态 |
| `AUTH_CODE_TOO_FREQUENT` | 429 | 发送冷却未结束 |
| `AUTH_UNAUTHENTICATED` | 401 | 凭证缺失、格式错误、已过期或退出；同时返回 `WWW-Authenticate: Bearer` |
| `USER_DISABLED` | 403 | 用户被禁用 |
| `AUTH_CODE_UNAVAILABLE` | 503 | 模拟短信未启用，真实短信尚未接入 |
| `DEPENDENCY_UNAVAILABLE` | 503 | RPC、MySQL 或 Redis 故障；不会伪装成验证码错误或放行 |

## 3. 模块职责与调用链

`live-api` 和 `live-user-provider` 是两个独立 Java 进程；`live-user-interface` 是两边共享的普通依赖包。

```text
客户端 HTTP
  → AuthController：解析请求和 Bearer，转换对外 UserView
  → AuthApplicationService：调用 RPC、关闭自动重试、区分业务错误与依赖故障
  → Dubbo 跨进程
  → AuthRpcImpl
  → AuthService：编排验证、注册、签发会话
      → AuthStore：Redis 验证码和会话
      → LoginAccountService：MySQL 事务
          → UserPhoneRepository：手机号绑定表
          → UserService：已有用户业务，复用创建及事务提交后缓存失效
```

API 不连接 Redis，也不能直接传用户 ID 换取登录会话。`AuthRpc` 新增独立契约，避免把验证码、Token 混入用户资料 CRUD。

`GET /api/users/me` 先从 Redis 找用户 ID，再在数据库事务中调用 `UserService.getById`。已有 UserService 在事务中直接查库、不走缓存，因此禁用判断不会依赖可能陈旧的用户缓存。代价是每次会话查询都访问 MySQL；以后可在明确失效规则后优化。

建议阅读顺序：`AuthController` → `AuthService.login` → 两段验证码 Lua → `LoginAccountService.findOrRegister` → `AuthStore.createSession/requireUserId/deleteSession` → 相关测试。

## 4. 手机号唯一与注册事务

新增 `sql/003-user-phone.sql`，创建 `t_user_phone`：`phone` 主键、`user_id` 唯一键，并用外键关联 `t_user.id`。暂定一个手机号一个账户、一个账户一个手机号，不实现换绑或多个登录方式。旧调试用户无需填充假手机号，也不会自动合并到登录账户。

使用独立绑定表可以保留原有 UserDTO 和用户缓存结构。当前学习版手机号明文存入绑定表和验证码 Key，不出现在公开资料响应中；没有实现手机号加密存储或脱敏管理系统。

首次登录事务包含“创建 t_user + 写 t_user_phone”。用户创建复用原有提交后失效事件：绑定失败时整个事务回滚，事件不会在回滚后删除缓存。

例如请求 A、B 都查到手机号未注册：

1. A、B 分别创建用户并尝试绑定手机号。
2. 唯一约束只允许一个绑定成功；失败方抛出 `DuplicateKeyException`。
3. 失败方的事务整体回滚，包括新建用户，避免孤立用户记录。
4. **在回滚完成后开启新事务**，查询已成功绑定的用户。不能在旧事务中吞掉异常继续使用旧快照。

这里使用 `TransactionTemplate` 和 `REQUIRES_NEW` 明确划定事务边界，确保返回 AuthService 时提交已经完成。唯一约束是最终防重依据，缓存重建锁不参与注册正确性。设计方式参考 [Spring 编程式事务说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html)。

## 5. 验证码与 Token 的 Redis 设计

默认 Key：

| Key | 内容与期限 |
| --- | --- |
| `live-platform:dev:auth:v1:code:<phone>` | Hash：`code/attempts/expiresAt/nextSendAt`；TTL 取验证码与冷却时间较大值 |
| `live-platform:dev:auth:v1:session:<sha256(token)>` | 用户 ID 字符串；默认 TTL 604800 秒 |

`issue-login-code.lua` 在同一次执行中检查冷却、覆盖新验证码、清零错误次数和设置 TTL。时间来自 Redis `TIME`，不同 Provider 的机器时钟不会影响发送冷却判断。

`consume-login-code.lua` 原子检查过期、比较验证码、记录失败或删除验证码字段，保证同一个验证码并发登录最多一个请求通过。成功时只移除 `code`，保留发送冷却；输错达到上限也移除 `code`，即使随后输入正确值仍失败。验证码的业务期限独立于 Hash TTL：当冷却时间更长时，Hash 仍在，但过期验证码不能登录。两段脚本都只访问一个 Key；调用方式参考 [Redis EVAL 文档](https://redis.io/docs/latest/commands/eval/)。

Token 使用 `SecureRandom` 生成 32 字节随机数，经无填充 Base64URL 编码成为 43 个字符；Redis Key 使用其 SHA-256 摘要。通过带 TTL 的 `SET NX` 一次完成创建。这里没有 JWT、刷新 Token 或自动续期机制；Redis 查询结果是会话是否有效的依据。

鉴权存储失败必须报错。用户资料缓存可以回源 MySQL，登录凭证却不能在 Redis 不可用时信任客户端传来的身份。API 的依赖故障日志仅记录 requestId 与异常类型，避免 RPC 异常文本带入验证码或 Token；需要排查时按请求链路定位，不在日志中打印请求密钥。

## 6. 跨 MySQL 与 Redis 的失败边界

验证码先消费，再进行注册事务，提交成功后才创建 Token。这三个步骤不是一个分布式事务。

| 失败位置 | 实际结果与恢复 |
| --- | --- |
| 验证码过期或不匹配 | 不访问注册逻辑、不创建会话 |
| 消费验证码后数据库失败 | 无新会话；验证码已用，需要冷却后重新获取 |
| 注册成功后会话写入失败 | 用户已存在，但本次登录返回 503；下次登录复用该账户 |
| Redis 命令或 RPC 超时 | 结果可能已生效；不自动重试消费或登录，不声称操作一定没发生 |
| 会话已创建但响应丢失 | 客户端可能拿不到 Token；该记录到期自动清理，可重新登录 |
| 退出与请求同时发生 | 退出之后的新鉴权失败；已经通过鉴权的在途请求不会被撤回 |

禁用用户不能登录，已有 Token 查询也返回 403；本阶段没有管理端禁用接口，也没有批量删除此用户所有 Token。重新启用后，尚未过期的原 Token 可以继续使用。

## 7. 配置与启动

| Provider 环境变量 | 默认值 |
| --- | --- |
| `AUTH_MOCK_ENABLED` | `false`；仍要求 `local` profile |
| `AUTH_KEY_PREFIX` | `live-platform:dev:auth:v1:` |
| `AUTH_CODE_TTL_SECONDS` | `300` |
| `AUTH_RESEND_SECONDS` | `60` |
| `AUTH_MAX_ATTEMPTS` | `5` |
| `AUTH_SESSION_TTL_SECONDS` | `604800` |

配置启动时检查范围：验证码/冷却 1～600 秒，错误次数 1～10，会话 1～2592000 秒。缩短会话配置只影响之后创建的 Token。

已有库先确认执行过 `002-user.sql`，再执行 `003-user-phone.sql`。新建空数据卷由 Compose 按序初始化；已有卷不会自动补表。PowerShell 示例：

```powershell
Set-Location D:\LivingPlatformByMyself
Get-Content -Raw -Encoding UTF8 sql/003-user-phone.sql | docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u live_app live_platform'
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d redis
mvn -f backend/pom.xml -DskipTests package
```

Compose 将 Redis 改为 `noeviction`：缓存与会话仍共用学习实例，但不能因 LRU 淘汰验证码限流状态而绕过限制。内存满时写操作失败，缓存可回源，登录返回 503。原阶段 05/06 文档中的 `allkeys-lru` 描述是当时的缓存配置，以本阶段配置为准。Redis 仍未开启持久化，重启后会话全部失效，验证码和冷却记录也会丢失；当前仅适用于本地学习，后续部署应隔离认证与缓存资源。

终端 A 启动 Provider：

```powershell
$env:MYSQL_PASSWORD = '填写本地数据库密码'
$env:AUTH_MOCK_ENABLED = 'true'
java -jar backend/live-user-provider/target/live-user-provider-0.1.0-SNAPSHOT.jar --spring.profiles.active=local
```

终端 B 启动 API（无需激活 `local`，避免同时开放任意用户调试操作）：

```powershell
java -jar backend/live-api/target/live-api-0.1.0-SNAPSHOT.jar
```

按 `scripts/auth.http` 依次获取验证码、登录、查询自己、退出、验证旧 Token 被拒绝，再重新登录比较用户 ID。手工验证过期可把 Provider 的 `AUTH_SESSION_TTL_SECONDS` 暂设为 `5`，重启并创建新会话，等待 5 秒后查询应返回 401。

## 9. 局限与下一阶段

当前只有手机号维度限流，没有 IP/设备维度限制、真实短信发送、风控、换绑、注销、单端互踢或会话刷新。手机号作为本地测试数据使用；当前不能验证真实号码所有权。

本轮阅读了参考项目的 `UserLoginServiceImpl`、`UserPhoneServiceImpl`、`AccountTokenServiceImpl`。沿用验证码登录、手机号映射与 Redis Token 思路；本项目增加验证码原子消费、数据库唯一约束与完整注册事务，采用 Bearer 请求头，并暂时把认证放在现有 Provider，避免新增尚不必要的进程。
