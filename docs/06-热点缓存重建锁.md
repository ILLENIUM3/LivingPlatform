# 热点缓存重建锁

日期：2026-11-10。阶段：用户缓存增强。对外接口和数据库表结构不变。

## 1. 为什么开发这一功能

热门主播的缓存过期时，很多请求可能同时发现 Redis 没有该用户，然后一起查询 MySQL。空值缓存解决重复查询不存在的用户，TTL 抖动分散不同 Key 的过期时间，都不能单独解决同一个热点 Key 的并发重建。

本次按用户 ID 为缓存重建增加一个短期租约，让正常情况下一个请求负责查库回填，其他请求短暂等待结果。它是性能优化，不是用户修改、扣款或库存操作的正确性锁。

参考 qiyu-live `SimpleRedisLock` 和 `unlock.lua` 的 SET NX、唯一标识及 Lua 解锁思路；本项目为每次获取锁生成 UUID，并进一步在回填时检查当前所有权。

## 2. 接口为什么保持不变

前端仍调用 GET `/api/dev/users/{id}`，API 仍通过 `UserRpc.getById` 查询用户。缓存如何重建属于 Provider 内部实现，调用方不需要传递锁参数或知道 Redis Key。

`Supplier<UserDTO>` 可以理解为“稍后再执行的查库函数”。只有缓存未命中且流程需要回源时，才调用它的 `get()`；返回 null 表示不存在，抛异常表示查询失败。

Provider 新增内部接口：

| 方法 | 含义 |
| --- | --- |
| `UserCacheLoader.get(userId, loader)` | 组织查缓存、抢锁、等待、查库；loader 是实际查库函数，返回 null 表示不存在 |
| `CacheRebuildLock.tryAcquire(userId)` | 返回 ACQUIRED、BUSY 或 UNAVAILABLE；成功时返回本次独有 token |
| `CacheRebuildLock.release(userId, token)` | 只释放仍属于该 token 的锁 |
| `UserCache.putIfOwned(userId, user, token)` | 仍持锁才原子回填；user 为 null 时写短期空值缓存 |

不能把“锁忙”和“Redis 不可用”都当成 false：锁忙可以等待其他请求的结果，Redis 不可用则立即降级查库。

## 3. 实际调用路径

```text
Controller → UserApplicationService → Dubbo → UserRpcImpl → UserService.getById
  → 参数校验
  → 若在数据库事务中：直接查库，不回填缓存
  → UserCacheLoader
      → 关闭缓存：直接查库
      → 缓存命中：返回资料或空值结果
      → 缓存未命中：尝试获取该用户的锁
          → 成功：二次查缓存 → 必要时查库 → 持锁回填 → finally 解锁
          → 锁忙：短暂随机等待 → 重查缓存 → 时间允许时再尝试
          → Redis 故障 / 等待超时：查库，但不回填缓存
```

空值结果仍由 UserService 转为 `USER_NOT_FOUND`。查询数据库抛异常时不会写空值缓存；否则一次数据库故障会被错误记成“用户不存在”。

## 4. 按顺序阅读代码

1. `UserService.getById`：业务层只传入查库函数，依然负责“不存在”的业务语义。
2. `UserCacheLoader.get`：本轮核心流程，先看抢锁成功分支，再看等待与降级。
3. `CacheRebuildLock.tryAcquire`：一次 SET NX 加上租约，不拆成 SETNX 再 EXPIRE。
4. `release-rebuild-lock.lua`：比较 token 与删除锁必须原子执行。
5. `UserCache.putIfOwned` 与 `fill-user-cache-if-owned.lua`：回填也检查所有权。
6. `CacheRebuildLockProperties` 与 YAML：区分租约时间和请求等待时间。

Java 类位于 `backend/live-user-provider/src/main/java/com/liveplatform/user/provider`，Lua 位于同模块 `src/main/resources/redis`。

## 5. 关键选择与原因

### 每个用户一个锁

缓存 Key 例如 `live-platform:dev:user:v1:12`，对应锁 Key 为 `live-platform:dev:user:v1:12:rebuild-lock`。查询用户 12 不会阻塞用户 13。多台 Provider 使用同一个 Redis 和相同前缀，才会竞争同一把锁。

### 为什么拿锁后再查缓存

A 读缓存未命中后暂停；B 获取锁、回填并释放；A 恢复后也成功拿到锁。若 A 不再次检查，就会重复查库。二次检查让 A 直接使用 B 的结果。

### 为什么锁有期限，且每次 token 不同

锁期限避免进程退出后永远占锁。独有 token 则区分不同次持锁：A 租约过期后 B 拿到同一 Key，A 结束时不能直接 DEL，必须比较所有权。只用固定用户 ID 或可重用的线程 ID 不足以表达每次持锁身份。

### 为什么解锁安全还不够

A 查询很慢，租约过期；B 已重新拿锁并回填新数据。即使 A 不会误删 B 的锁，直接 SET 缓存仍可能覆盖 B 的数据。因此回填 Lua 把“比较 token”和“写缓存并设置 TTL”放在一次原子操作中。A 失去租约时仍可把自己的查询结果返回调用方，但不能再写缓存。

### 为什么不无限等待

默认只等待 200ms，期间随机等待 1～40ms 后重查缓存。超时后选取可用性，允许直接查库，但不回填；避免不持锁的降级请求覆盖持有者的数据。

等待时间是是否继续尝试的预算，不是整个请求的硬超时。正在执行的 Redis 命令可能超过预算，后面还需要数据库查询；Redis 超时、数据库超时和 RPC 超时要共同评估。线程中断会保留中断标志并停止等待，由现有 API 故障处理返回 503。

## 6. 配置、部署与局限

无需新 SQL 或新依赖，Redis 仍使用上一阶段实例。重新打包并重启 Provider 后生效。

| 环境变量 | 默认 | 含义 |
| --- | --- | --- |
| USER_CACHE_LOCK_LEASE_MILLIS | 5000 | 锁存活期限，不是数据库查询超时 |
| USER_CACHE_LOCK_WAIT_MILLIS | 200 | 竞争者继续等待、重试的时间预算；0 表示不等待 |
| USER_CACHE_LOCK_POLL_MILLIS | 40 | 单次随机等待上限，避免同步重试 |

本版不续租、不重入，不实现 Redlock，也不是数据库写入使用的 fencing token 机制。租约过期或 Redis 重启时允许多个请求查询数据库；令牌检查只约束 Redis 回填和解锁。

当前 Redis 使用 allkeys-lru，内存压力也可能提前淘汰锁。由于这是可降级的缓存优化锁，我们接受这种情况下出现重复回源；绝不能把它直接复用于扣款或库存正确性。关键业务锁需要另外选择资源隔离与存储策略，并依靠数据库约束兜底。

回填脚本访问锁 Key 和数据 Key，当前用于单机 Redis。迁移 Redis Cluster 时须设计相同 hash tag，使两个 Key 位于同一槽，不能直接套用现有命名。

本轮仍未消除数据库更新与缓存回填之间的竞态：修改资料的事务没有获取重建锁，某个读请求即使仍合法持锁，也可能将更新前读到的数据回填。事务提交后删除失败、进程退出也仍由 TTL 收敛，后续再实现可靠失效事件与重试。

新增六个聚焦测试，验证二次检查、锁忙降级、Redis 故障降级、数据库异常后解锁、不存在用户的持锁回填，以及缓存关闭时完全绕过锁。
