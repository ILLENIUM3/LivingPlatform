# 阶段 01：工程搭建与验收

日期：2026-11-08

## 1. 本阶段目标

建立自己的 Maven 多模块后端，启动 API 和用户服务，通过 Nacos 服务发现完成真实 Dubbo 调用，再读取 MySQL 的初始化记录。用户表、用户增改查和登录属于后续阶段。

## 2. 本轮环境与版本决策

开发终端是 WSL，实际项目位于 `D:\LivingPlatformByMyself`（WSL 路径 `/mnt/d/LivingPlatformByMyself`）。应用提交的工作目录发生了 Windows/WSL 路径转换错误，因此开发时在临时目录完成构建，再把工程文件同步回真实项目。

检查结果：WSL 有 OpenJDK 21.0.12.1、Maven 3.9.12；Redis 的 6379 端口可达，本阶段未修改或使用。默认 MySQL、Nacos 端口未开放。Docker Desktop 已安装，本轮启动后使用项目独立容器准备依赖。

| 项目 | 决策 | 原因 |
| --- | --- | --- |
| Java | 编译目标 17，运行时 21 | 保留参考项目语言基线，复用现有 JDK |
| Spring Boot | 3.5.16 | 继续使用 Boot 3 系列，官方系统要求允许 Java 17～25 |
| Dubbo | 3.3.7 | 使用正式发布版本，通过官方 Nacos Starter 接入注册中心 |
| Nacos | 2.5.1 单机 | 当前只需要服务发现；本地配置仍在应用 YAML |
| MySQL | 8.4.7 | 项目独立实例、独立数据卷；不连接或改写其他项目的数据 |
| 数据访问 | JdbcTemplate | 第一阶段只执行探针查询；用户业务阶段再引入所需的 Mapper 能力 |
| Spring Cloud Alibaba | 本阶段未引入 | 当前 Dubbo Starter 已完成 Nacos 注册发现；后续需要对应功能时再引入 |

依赖版本在父 POM 中统一管理；MySQL 驱动和测试库沿用 Spring Boot 的依赖管理。依赖组合除查阅官方文档外，还需要以下构建和实际联调结果验证。

官方依据：

- [Spring Boot 3.5 系统要求](https://docs.spring.io/spring-boot/3.5/system-requirements.html)
- [Dubbo Spring Boot Starter](https://dubbo.apache.org/en/overview/mannual/java-sdk/reference-manual/config/spring/spring-boot/)
- [Dubbo Nacos 注册中心](https://dubbo.apache.org/en/overview/mannual/java-sdk/reference-manual/registry/nacos/)

## 3. 代码阅读顺序

以 `backend` 为起点，按下面顺序阅读：

1. `pom.xml`：聚合模块、Java 编译目标、依赖版本管理。
2. `live-user-interface/.../UserProbeRpc.java`：跨进程调用契约。
3. `live-user-interface/.../UserProbeResult.java`：服务间传输的数据。
4. `live-user-provider/.../DatabaseProbeService.java`：实际执行数据库查询。
5. `live-user-provider/.../UserProbeRpcImpl.java`：用 `@DubboService` 暴露接口。
6. `live-api/.../SystemProbeService.java`：用 `@DubboReference` 调用远端服务。
7. `live-api/.../SystemController.java`：把链路暴露为 HTTP 接口。
8. `live-api/.../ApiExceptionHandler.java`：将依赖失败转为 503，并记录 requestId。
9. 两个 `application.yml`：分别设置 HTTP、RPC、注册中心和数据源。

一次请求的执行路径：

```text
浏览器 / HTTP 工具
  → SystemController
  → SystemProbeService
  → Dubbo Consumer 从 Nacos 获取 Provider 地址
  → TCP RPC 请求（20880）
  → UserProbeRpcImpl
  → DatabaseProbeService
  → MySQL platform_bootstrap 表（13306）
  → DTO 返回 API
  → ApiResponse JSON
```

Nacos 是服务发现组件，业务请求不会经由 Nacos 中转。API 不直接访问 MySQL，也没有依赖用户 Provider 的实现包。

## 4. 数据库与配置

`sql/001-bootstrap.sql` 只创建一个探针表，并插入 `id=1, probe_value=stage01-ready`。重复执行不会覆盖已有记录。

Docker 首次初始化时创建 `live_platform` 数据库和 `live_app` 应用用户，再执行 SQL。用户服务使用应用用户连接。应用启动不会自动重建表。

Compose 对外端口：MySQL 13306、Nacos HTTP 18848、Nacos gRPC 19848。端口限制为本机访问；Java 应用默认使用本机地址，RPC 广播地址也是 127.0.0.1。

本地密码保存在忽略提交的 `deploy/.env` 中。Compose 会读取它，但单独启动的 Java 进程不会自动读取这个文件，需要传入 `MYSQL_PASSWORD` 环境变量。

## 5. 验收标准与测试分工

| 检查 | 成功标准 |
| --- | --- |
| Maven 构建 | 四个模块全部构建成功，API 和 Provider 各生成可执行 JAR |
| 数据库测试 | 修改记录后下一次查询立即返回新值；缺表、缺记录均失败 |
| API 测试 | 远端成功返回统一结构；RPC/数据库异常返回 503，不泄露内部错误文本 |
| 容器健康 | MySQL、Nacos 均 healthy |
| 服务发现 | Nacos 中可看到用户服务实例 |
| 实际 HTTP → RPC → MySQL | HTTP 200，返回真实 MySQL 产品名、数据库名和初始化值 |
| 实际故障与恢复 | 停止依赖时调用失败；恢复依赖后重新调用成功 |

三个数据库测试使用 H2，三个 HTTP 测试替换 RPC 依赖，用于快速验证本层行为。跨进程通信、注册发现和 MySQL 兼容性由真实环境联调验证。

具体启动命令见根目录 README。IDEA HTTP 请求文件为 `scripts/requests.http`，Windows 验收脚本为 `scripts/smoke-test.ps1`。

阶段 01 已完成，以下结果来自此前已经执行的验证，本次收尾没有重新测试：

- Maven 四个模块构建成功，生成 API 和 Provider 两个可执行 JAR。
- 六个自动化测试通过，失败数与错误数均为 0。
- Nacos 注册列表中存在 `live-user-provider`。

- 修改数据库探针值后，接口返回值随之变化，随后已恢复初始化值。
- MySQL 停止时返回 503，重新启动后恢复成功。
- 用户服务停止时返回 503，重新启动后恢复成功。
- WSL 侧 `scripts/smoke_test.py` 执行通过。

实际结果保存在忽略提交的 `.runtime/stage01-verification.json`；两个 Java 验证进程已停止，项目 MySQL/Nacos 容器保留运行。部署启动顺序见 README。

Windows PowerShell 本次无法直接访问 WSL 内 Java 进程的 localhost 端口。Windows 运行 Java 时使用 PowerShell 验收脚本；WSL 运行 Java 时使用 Python 验收脚本。Windows 同侧 Java 启动方案尚未实际验证。

首次 Maven 下载曾因未使用终端代理停滞，本轮通过临时 Maven settings 配置现有代理解决，没有修改全局设置。重新构建需要可访问 Maven Central；如使用代理，应在运行 Maven 的对应环境中配置。

Dubbo 核心依赖与注册中心依赖分别由 `dubbo-spring-boot-starter` 和 `dubbo-nacos-spring-boot-starter` 引入，两者均锁定 3.3.7。
